# 64. A pack for Microsoft SQL Server

Asked for on 2026-11-20: "very detailed". A pack, `mssql`, for SQL Server
2019, 2022 and 2025, on Linux and Windows, watched from Linux, macOS and
Windows, read-only, with everything SQL Server says about itself that is
cheap to read and carries no query text.

## What it is

Fifteen jobs, each one T-SQL query that prints finished metric lines, tag
values made safe by the query itself (anything outside `A-Za-z0-9_.-`
becomes `_`, character by character), so the bash script (Linux, macOS)
and the PowerShell one (Windows) print the same lines. The scripts are
generated by `tools/mssql/gen.py` from `tools/mssql/sql/`; packs/README.md
has every job.

- **Linux and macOS:** `sqlcmd`, Microsoft's ODBC one (`mssql-tools18`) or
  the Go one (`go-sqlcmd`), with only the options both share (`-Nm`, `-F`,
  `-l`, `-t`, `-h -1 -W -b -i`).
- **Windows:** .NET's own `System.Data.SqlClient`, in Windows PowerShell 5.1
  (`System.Data`) and PowerShell 7 (`System.Data.SqlClient` 4.6): nothing
  to install. `MSSQL_AUTH=windows` logs in as the account Vigil runs as.
- **The password** is in `SQLCMDPASSWORD`, from
  `secret:MSSQL_MONITOR_PASSWORD`, which both `sqlcmd`s read: never on a
  command line.
- **TLS, always, the certificate checked.** No setting turns that off. On
  Linux, `MSSQL_CACERT` goes to the client as `SSL_CERT_FILE`, which both
  honour; Microsoft's `sqlcmd` matches names, not IP addresses
  (`MSSQL_CERT_NAME` for `-F`). On macOS the Go `sqlcmd` ignores
  `SSL_CERT_FILE` and trusts the System keychain only, and a run that fails
  that way says so. On Windows, the machine's trusted root store. Pinning a
  server's certificate (`-J`) was left out: Microsoft's `sqlcmd` pins only in
  strict mode, which needs the server set up for it.
- **Each query** waits at most 5 seconds for a lock, reads uncommitted,
  gives way in a deadlock, and stops at its first error
  (`XACT_ABORT`), so a run never prints half its readings. Lists are capped
  under Vigil's 1000 lines a run.

## The login

```sql
CREATE LOGIN vigil_monitor WITH PASSWORD = '...';
-- 2022 and 2025:
GRANT VIEW SERVER PERFORMANCE STATE, VIEW SERVER SECURITY STATE, VIEW ANY DATABASE, CONNECT ANY DATABASE TO vigil_monitor;
-- 2019:
GRANT VIEW SERVER STATE, VIEW ANY DATABASE, CONNECT ANY DATABASE TO vigil_monitor;
```

Found while testing, as the login:

- `sys.master_files` shows nothing without `VIEW ANY DEFINITION`; each
  database's own `sys.database_files`, by three-part name, does with
  `CONNECT ANY DATABASE`, which reads no table.
- `SQLAgentReaderRole` gives no `SELECT` on Agent's tables (it works through
  Agent's procedures): `mssql_agent` needs `SELECT` on `msdb`'s `sysjobs`,
  `sysjobhistory`, `sysjobactivity` and `syssessions`, and without them
  reports `readable 0` rather than fail every 15 minutes.
- `sys.availability_groups` shows a group only with `VIEW DEFINITION` on it:
  without that, `mssql_replication` tags a group by its id.
- `msdb`'s backup history and `suspect_pages` are readable by `public`.
  Log shipping's tables are not, and the TDE certificates in `master` are
  not visible: both were left out, rather than ask for more.
- On Linux, SQL Server records idle CPU as 0, so the rest of the machine's
  CPU (`other_pct`) is on Windows only; and it records its own CPU once a
  minute, so `sql_pct` is left out in its first minute.

## Done

- Linux, by `tests/integration/backends/scripts/run-mssql.sh` on the Fedora
  test machine, Developer edition in Docker, TLS only with a test CA:
  `service-packs.sh` through Vigil, 79 passed, 0 failed on 2019 (CU32) and
  2025 (CU11), each the primary of a read-scale availability group whose
  secondary was stopped and started; 71 passed, 0 failed on 2022 (CU28)
  alone (`--no-replica`). On 2022 CU28 the secondary would not join a group
  in Docker there: the join timed out while the secondary held a CPU, with
  TLS, the endpoints' encryption and name resolution each ruled out; 2019
  and 2025, set up the same way, joined. Every job printed the same lines
  with Microsoft's `sqlcmd` 18.7 as with the Go one, against 2022.
- Windows: every job on Windows PowerShell 5.1 and PowerShell 7, the same
  lines as Linux, then `Service-Packs.ps1` through Vigil, 53 passed, 0
  failed on each.
- macOS: every job under bash 3.2 with the Go `sqlcmd`, then
  `service-packs.sh` through Vigil, 69 passed, 0 failed.
- CI: SQL Server 2022, TLS only, in the service-packs job.
- Evidence: `tests/integration/backends/reports/runs/2026-11-20/`
  (`fedora/pack-mssql-*`, `windows/pack-mssql-windows`,
  `macos/pack-mssql-macos`).
